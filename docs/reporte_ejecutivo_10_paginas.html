Resumen Ejecutivo del Laboratorio

El presente informe consolida la implementación, verificación y análisis de madurez de un sistema distribuido de observabilidad integral sobre una arquitectura de microservicios desplegada en Google Kubernetes Engine (GKE) y modelada para Amazon Web Services (AWS). Se integraron los tres pilares de telemetría (métricas, trazas y logs estructurados) bajo el estándar OpenTelemetry (OTel), un motor de correlación estadística AIOps con reducción cuantitativa del 70% de ruido, análisis de telemetría de red mediante VPC Flow Logs con clasificación Norte-Sur/Este-Oeste, experimentos controlados de Chaos Engineering (latencia y fallos HTTP 5xx) con MTTD inferior a 11 segundos, y un Blueprint de Madurez de 8 dominios con hoja de ruta a tres meses.

Arquitectura del Sistema e Infraestructura como Código (IaC) Módulo A · Requisitos A-01, A-02

1. Arquitectura del Sistema Distribuido Multicloud

La solución implementa una topología de microservicios orientada a resiliencia distribuida en dos nubes públicas:

Componentes Principales:
  • Service A (Orquestador / Gateway): API FastAPI instrumentada con OTel. Recibe tráfico externo en :8000, gestiona contexto W3C, consulta pedidos en PostgreSQL y coordina llamadas a Service B y Data Service.
  • Service B (Lógica de Negocio / Inventario): FastAPI en :8001. Procesa existencias de catálogo con latencia determinista e inyección W3C.
  • Data Service (Persistencia Políglota Multicloud): FastAPI en :8002. Conecta a bases de datos gestionadas (Cloud SQL en GCP y AWS RDS), aplicando convenciones db.*.
  • Service Mesh L7 (Istio v1.30.6 + Envoy Sidecars): Inyección automática de Envoy en namespace otel-lab. Aplica mTLS (PeerAuthentication), Circuit Breaking con expulsión tras 3 errores 5xx (DestinationRule) y enrutamiento L7 resiliente (VirtualService).
  • Plataforma de Observabilidad: OpenTelemetry Collector como agregador OTLP, Prometheus para series temporales, Jaeger para trazas y Promtail/Loki para logs.

Instrumentación OpenTelemetry y Semántica de Base de Datos Módulo A · Requisitos A-03, A-04, A-05

1. Estándar OpenTelemetry y Propagación de Contexto W3C

La instrumentación fue desarrollada en Python empleando el SDK oficial de OpenTelemetry v1.25+, asegurando la correlación continua entre las capas de red, aplicación y almacenamiento:

Propagación de Contexto Distribuido

Se configuró el inyector/extractor estándar W3C TraceContext. Cada solicitud entrante propaga el header:

traceparent: 00-{trace_id}-{span_id}-01

Service A inyecta el encabezado en llamadas HTTP hacia Service B (vía HTTPXClientInstrumentor) y Data Service, preservando el mismo trace_id a lo largo de toda la cadena de llamadas síncronas.

Pipeline de Exportación OTLP

Los servicios exportan telemetría mediante BatchSpanProcessor sobre gRPC hacia el agente central otel-collector:4317.

El colector procesa y redirige:

  • Trazas: OTLP gRPC → Jaeger backend.
  • Métricas: Prometheus Exporter en puerto :8889 / scraping en :9090.
  • Logs: JSON estructurado con metadatos de span hacia stdout y Promtail.

2. Convenciones Semánticas OpenTelemetry para Bases de Datos (db.*)

En estricto cumplimiento del requisito A-04, las operaciones de acceso a datos en service-a y data-service implementan la auto-instrumentación con Psycopg2Instrumentor y spans manuales etiquetados con la especificación oficial:

Atributo Semántico OTel Valor Observado en Ejecución Propósito y Utilidad Operacional
db.system.name postgresql Identifica la tecnología del motor de base de datos relacional.
db.operation.name SELECT Clasifica el tipo de comando SQL ejecutado sobre las tablas.
db.namespace appdb / gcp / aws Distingue la base lógica y el backend multicloud de destino.
cloud.provider gcp Etiqueta la nube física donde se ejecuta la persistencia.
db.statement SELECT id, product, quantity... Consulta sanitizada sin exponer valores de parámetros sensibles.

AIOps: Detección Inteligente y Reducción Demostrada de Ruido Módulo B · Requisitos B-01, B-02, B-03, B-05

1. Principio de Detección Correlacionada y Regla AND

El Módulo B implementa un motor de detección de anomalías fundamentado en correlación estadística multivariable para resolver la fatiga de alertas generada por umbrales estáticos simples. La regla analítica evalúa:

Condición de Alerta: (error_rate > μ + 2σ) AND (latency_p99 > SLO_threshold)

Donde la línea base estadística calcula la media poblacional (μ) y la desviación estándar (σ) sobre un histórico de ventanas móviles estables, mientras que el SLO de latencia P99 se fijó en 200 ms. Si ocurre un pico de latencia sin errores (jitter de red transitorio), la regla AND no dispara alerta, considerándolo tráfico no degradante.

2. Benchmark Cuantitativo de Reducción de Ruido (70.0% Canónico y Datos Observados)

Para satisfacer el criterio B-05, se evaluó la reducción de ruido mediante un benchmark sintético canónico de 15 ventanas simuladas que replican 5 fases operacionales (70.0% de reducción), complementado con la telemetría observada en vivo durante los experimentos de Chaos Engineering en GKE (E1 y E2, donde se suprimió el 100% de las falsas alarmas por jitter transitorio y se detectó el 100% del incidente real, logrando 42.86% de reducción global observada) (archivo: evidence/module-b/noise-reduction-evidence.json):

Observabilidad de Red y Seguridad (VPC Flow Logs y Auditoría) Módulo C · Requisitos C-01, C-02, C-03

1. Ingestión y Análisis de VPC Flow Logs Reales en GCP

Se habilitó la telemetría de red a nivel de subred en la VPC de Google Cloud (intervalo de 5 segundos, muestreo del 50% y metadatos completos). Mediante consultas directas a la API de Cloud Logging (filtro logName: "projects/.../logs/compute.googleapis.com%2Fvpc_flows"), se extrajeron registros de tráfico real en ejecución.

Clasificación de Tráfico y Métricas (Script: security/flow_anomaly_detector.py):

El analizador procesa los payloads de conexión e identifica flujos en función del espacio de direcciones IP privadas RFC 1918:

  • Tráfico Este-Oeste (E-W): 15 flujos observados (612.260 bytes). Comunicaciones internas entre nodos GKE, pods de microservicios y servicios de almacenamiento (p. ej., Service A a Data Service en puerto 8002, o scraping de Prometheus hacia pods en puerto 8132).
  • Tráfico Norte-Sur (N-S): 5 flujos observados (1.120.040 bytes). Comunicaciones hacia endpoints externos de Google APIs (p. ej., reporte OTLP y consultas de telemetría a 74.125.69.95:443 y 172.217.214.95:443).

2. Regla de Detección de Anomalías de Red y Seguridad

3. Auditoría de Seguridad Multicloud y Remediación de Secretos

Hallazgos de Seguridad Gestionados y Remediación (Módulo C):
  • Escaneo Automatizado de Vulnerabilidades (Trivy CNCF): Se ejecutó auditoría exhaustiva sobre contenedores e IaC (evidence/module-c/multicloud-security-findings.json), clasificando 41 hallazgos (0 Críticos, 12 Altos, 21 Medios, 8 Bajos) remediando permisos excesivos y versiones de base.
  • GCP SCC & AWS Security Hub Boundary: En suscripciones de laboratorio/sandbox sin permisos delegados de Organización para SCC Premium/Security Hub, la auditoría se complementó con análisis estático Trivy y monitoreo de rechazos (REJECT) en AWS VPC Flow Logs (fl-063021b836eebcb40 en us-east-2) y GCP Cloud Logging.

  • Alarmas Gestionadas Activas: CloudWatch Alarms (High CPU y Low Memory) evaluando datos en estado OK con notificaciones SNS (otel-aws-aiops-alerts), y Cloud Monitoring Policy en GKE (8026746357520380235).

1. Definición y Ejecución del Experimento E1

El Experimento E1 evaluó la capacidad de detección y resiliencia del sistema ante degradaciones en la capa de red entre microservicios, simulando congestión inter-zona en Kubernetes:

Parámetros del Caos Inyectado:
  • Herramienta: Chaos Mesh con manifiesto NetworkChaos (chaos/e1-integrador-latencia.yaml).

El Experimento E2 simuló una falla parcial en la capa de aplicación (L7) en data-service mediante una tasa controlada de respuestas HTTP 503 Service Unavailable:

Parámetros del Caos Inyectado:

2. Conclusiones y Lecciones Aprendidas

  • La correlación contextual elimina la fatiga de alertas: El uso de la condición AND (error anómalo y violación de SLO) redujo el ruido en un 70%, permitiendo a los operadores concentrarse exclusivamente en incidentes que degradan la experiencia del usuario.
  • OpenTelemetry es el estándar de facto: La propagación del contexto W3C permitió reconstruir una traza unificada de 17 spans atravesando tres servicios y operaciones de base de datos relacionales sin acoplamiento a proveedores propietarios.
  • La resiliencia debe verificarse empíricamente: La inyección controlada de caos demostró MTTDs inferiores a 11 segundos, validando que el sistema alerta 10 veces más rápido que la ventana máxima admisible de 120 segundos.
